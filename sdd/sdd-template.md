## 1. Введение

### 1.1 Назначение документа
Документ SDD описывает архитектуру и проектные решения приложения DreamCart. Он предназначен для разработчиков, тестировщиков и руководителя проекта и используется при реализации, проверке и сопровождении системы. Документ связан со спецификацией требований SRS DreamCart версии 0.1 и записью архитектурного решения ADR-001.

### 1.2 Область применения
DreamCart — приложение для управления списками желаний, планирования накоплений и анонимного бронирования подарков. Пользователь добавляет товары вручную или по ссылкам на интернет-магазины, проверяет извлечённые сведения, указывает приоритет и накопленную сумму, а также делится публичным списком. В систему входят пользовательский интерфейс, прикладные сервисы и слой хранения данных. Оплата, оформление заказа и доставка товаров не входят в текущую версию.

#### 2.2.1 Контекст
Акторы: владелец списка и посетитель публичного списка. Внешние интернет-магазины (Ozon, Wildberries, Amazon, AliExpress и другие поддерживаемые сайты) являются источниками открытых сведений о товарах. DreamCart получает URL и пытается извлечь название, изображение, цену и магазин. Владелец управляет списком и бюджетом; посетитель просматривает публичный список и бронирует товар. Оплата и доставка находятся за границами системы.

#### 2.2.2 Композиция
Корневой компонент `DreamCartApplication` объединяет:
1. `MainWindow` — интерфейс: `WishListPanel`, `UrlParserPanel`, `ReservationView`, `BudgetDashboard`.
2. `ApplicationLogic` — сервисы: `UrlParserService`, `ReservationEngine`, `BudgetForecaster`, `NotificationService`.
3. `Database` — хранение: `WishRepository`, `ReservationStore`, `CacheManager`.

Разделение локализует изменения и позволяет тестировать сервисы независимо от UI.

#### 2.2.4 Физическое представление
Физическая инфраструктура пока не определена. Предполагается Java-приложение и постоянное хранилище. Если публичные списки должны открываться на устройствах друзей через интернет, потребуется серверная часть или веб-развёртывание, HTTPS и доступное извне хранилище. ОС, СУБД и хостинг необходимо уточнить до выпуска.

#### 2.2.5 Структура
Диаграмма SysML v2 показывает, что `DreamCartApplication` содержит `mainWindow`, `applicationLogic` и `database`. `MainWindow` включает четыре панели; `ApplicationLogic` — четыре сервиса; `Database` — репозиторий желаний, хранилище бронирований и кэш. `part def` задаёт определение типа компонента, а `part` — использование части внутри другого компонента. Композиция обозначает владение составными частями. Пунктирные линии визуализатора между определением и использованием не следует трактовать как поток данных. Для явного описания взаимодействий нужны интерфейсы и соединения.

|---|---|---|
| MainWindow | ApplicationLogic | Передача команд и получение результатов |

Зависимости направлены от компонента-потребителя к компоненту, предоставляющему нужную операцию.

#### 2.2.7 Информация
| Сущность | Основные атрибуты | Назначение |
|---|---|---|
| Wish | id, title, productUrl, imageUrl, storeName, price, currency, priority, savedAmount, status | Карточка желания |
| WishList | id, ownerId, title, publicToken, visibility | Список владельца |
| Reservation | id, wishId, status, createdAt | Статус бронирования |
| BudgetSettings | ownerId, monthlyBudget, currency | Бюджет |
| CacheEntry | key, payload, createdAt, expiresAt | Кэш |

Поля являются проектным предложением и уточняются при выборе СУБД. Личность посетителя не должна передаваться владельцу. Публичная ссылка должна использовать непредсказуемый токен.

#### 2.2.8 Интерфейс
| Операция | Вход | Результат |
|---|---|---|
| `UrlParserService.parse(url)` | URL товара | Данные товара или ошибка |
| `WishRepository.save(wish)` | Карточка желания | Сохранённая запись |
| `WishRepository.findById(id)` | ID желания | Запись или отсутствие |
| `ReservationEngine.reserve(wishId)` | ID желания | Успех или отказ |
| `ReservationStore.reserveAtomically(wishId)` | ID желания | Атомарная смена статуса |
| `BudgetForecaster.calculate(wishes, budget)` | Желания и бюджет | Дата или причина отказа |
| `NotificationService.notify(event)` | Событие | Уведомление |

Внешняя загрузка страниц выполняется по HTTP/HTTPS с проверкой URL и ограничением времени ожидания. Рабочее публичное взаимодействие должно использовать HTTPS.

#### 2.2.9 Взаимодействие
**Импорт:** пользователь вводит URL → `MainWindow` передаёт команду в `ApplicationLogic` → `UrlParserService` проверяет URL, загружает HTML и разбирает Jsoup → результат показывается пользователю → после проверки `WishRepository` сохраняет карточку → `WishListPanel` обновляется.

**Бронирование:** посетитель открывает публичный список → выбирает товар → `ReservationEngine` вызывает атомарную операцию `ReservationStore` → статус меняется на «Забронировано» → `NotificationService` сообщает результат → владелец видит только статус.

**Прогноз:** пользователь задаёт месячный бюджет → `BudgetForecaster` получает цену, накопления и приоритеты → рассчитывает дату → `BudgetDashboard` показывает результат.

#### 2.2.10 Алгоритм
**Импорт товара:**
```text
parseProduct(url):
    проверить схему URL (HTTP/HTTPS) и допустимость адреса
    проверить наличие актуального результата в кэше
    загрузить HTML с тайм-аутом
    разобрать документ через Jsoup
    извлечь название, изображение, цену и магазин
    при неполных данных вернуть частичный результат с предупреждением
    сохранить результат в кэш
    вернуть черновик для подтверждения пользователем
```

**Бронирование:**
```text
reserve(wishId):
    начать транзакцию
    проверить существование и доступность желания
    если уже забронировано — вернуть отказ
    атомарно установить RESERVED
    не раскрывать владельцу личность посетителя
    подтвердить транзакцию и отправить уведомление
```

**Финансовый прогноз:**
```text
forecast(price, savedAmount, monthlyBudget, priority):
    remaining = max(price - savedAmount, 0)
    если remaining == 0: сообщить, что сумма накоплена
    если цена неизвестна или бюджет <= 0: прогноз недоступен
    определить долю бюджета по утверждённому правилу приоритетов
    рассчитать число месяцев и ориентировочную дату
```
Правило распределения бюджета между несколькими желаниями пока не определено. До его утверждения прогноз должен использовать явно заданное ежемесячное отчисление для конкретной цели.

#### 2.2.11 Динамика состояний
**Состояния желания:**

| Текущее состояние | Событие | Новое состояние |
|---|---|---|
| Draft | Пользователь подтвердил карточку | Active |
| Active | Товар забронирован | Reserved |
| Reserved | Бронирование отменено по правилам системы | Active |
| Active | Желание удалено | Deleted |

**Состояния импорта:** `Idle → Validating → Fetching → Parsing → Review → Saved`. При ошибке операция переходит в `Failed`; пользователь может добавить товар вручную.

#### 2.2.12 Параллелизм
Бронирование одного желания несколькими посетителями должно выполняться атомарно в транзакции или через условное обновление/ограничение уникальности. Нельзя разделять чтение статуса и запись нового статуса без защиты от гонки. Сетевой парсинг должен выполняться с тайм-аутом и не блокировать UI.

#### 2.2.13 Паттерны
- **Layered Architecture:** разделение UI, прикладной логики и хранения.
- **Service Layer:** бизнес-операции в специализированных сервисах.
- **Repository:** доступ к желаниям и бронированиям через репозитории.
- **Cache-Aside:** проверка кэша перед повторной загрузкой страницы.

#### 2.2.14 Развёртывание
Предварительная схема включает Java-приложение, конфигурацию и постоянное хранилище. Для общедоступных списков потребуется серверный компонент, HTTPS и база данных на стороне сервера. Локальное настольное приложение без сервера не обеспечивает общий доступ между устройствами. Топология уточняется после выбора веб- или клиент-серверного варианта.

#### 2.2.15 Ресурсы
Основные ресурсы — сетевые соединения, память для карточек, постоянное хранилище и кэш. Для загрузки страницы устанавливается тайм-аут до 15 секунд (SRS REQ-PERF-002). Срок жизни и размер кэша ограничиваются конфигурацией. Список до 500 записей должен открываться не более чем за 2 секунды в согласованном тестовом окружении (REQ-PERF-001).

## 3. Проектные представления

### DV-001 — Архитектурный контекст
- **Viewpoint:** Контекст.
- **Representation:** Владелец управляет желаниями и бюджетом; посетитель открывает публичный список и бронирует товар; интернет-магазины предоставляют HTML-страницы.
- **More Information:** SRS REQ-FUNC-001—REQ-FUNC-009, REQ-SEC-002—REQ-SEC-003.

### DV-002 — Декомпозиция DreamCart
- **Viewpoint:** Композиция и структура.
- **Representation:** `DreamCartApplication` содержит `MainWindow`, `ApplicationLogic`, `Database`; их части перечислены в разделе 2.2.2.
- **More Information:** Диаграмма `DreamCart_SysMLv2.sysml`; REQ-MAINT-001.

### DV-003 — Импорт товара
- **Viewpoint:** Взаимодействие и алгоритм.
- **Representation:** `UrlParserPanel → ApplicationLogic → UrlParserService → CacheManager/внешний магазин → подтверждение пользователя → WishRepository`.
- **More Information:** REQ-FUNC-002, REQ-FUNC-003, REQ-PERF-002, REQ-SEC-001, REQ-REL-002.

### DV-004 — Анонимное бронирование
- **Viewpoint:** Взаимодействие, информация и динамика состояний.
- **Representation:** `ReservationEngine` атомарно меняет статус через `ReservationStore`; владелец получает только статус, но не личность посетителя.
- **More Information:** REQ-FUNC-007, REQ-FUNC-008, REQ-SEC-002, REQ-SEC-003, REQ-REL-003.

### DV-005 — Финансовый прогноз
- **Viewpoint:** Алгоритм.
- **Representation:** `BudgetForecaster` получает цену, накопления, месячный бюджет и приоритет; возвращает дату или причину невозможности расчёта.
- **More Information:** REQ-FUNC-004—REQ-FUNC-006. Правило распределения бюджета требует уточнения.

### DV-006 — Модель данных
- **Viewpoint:** Информация.
- **Representation:** Основные сущности: WishList, Wish, Reservation, BudgetSettings, CacheEntry.
- **More Information:** REQ-REL-001, REQ-SEC-002, REQ-OBS-001.

## 4. Решения

### ADR-001 — Трёхслойная модульная архитектура
- **Context:** Необходимо разделить интерфейс, бизнес-логику и хранение.
- **Options:** Монолит; трёхслойная архитектура; микросервисы.
- **Outcome:** Выбрана трёхслойная архитектура как компромисс между модульностью и сложностью реализации.
- **More Information:** `ADR-001-DreamCart.md`.

### ADR-002 — Jsoup для извлечения данных товара
- **Context:** Требуется импортировать название, изображение, цену и магазин по URL.
- **Options:** Ручной ввод; разбор HTML с Jsoup; коммерческие API магазинов.
- **Outcome:** Для первой версии выбран Jsoup; результат показывается пользователю для проверки и исправления.
- **More Information:** REQ-FUNC-002, REQ-FUNC-003, REQ-SEC-001.

### ADR-003 — Анонимное отображение бронирования
- **Context:** Владелец должен видеть, что подарок забронирован, но не знать дарителя.
- **Options:** Показывать имя; показывать только статус; не показывать статус.
- **Outcome:** Показывать только статус, не передавая владельцу идентификаторы посетителя.
- **More Information:** REQ-FUNC-008, REQ-SEC-003.
